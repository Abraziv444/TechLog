# TechLog v1.07.18

Мобильное веб-приложение (PWA) для учёта работ по восстановлению/клинингу апартаментов и пикапов оборудования. Дизайн — в духе Duolingo (тёмная тема). Одна работа = один юнит в апарт-комплексе = один PDF-инвойс по образцу бумажной формы «INVOICE #CC».

## ⚠️ Важно про безопасность
Пароль от базы данных Postgres (Direct connection) — секрет. Он нигде в приложении не используется и не должен попадать в репозиторий или переписку. Так как он уже пересылался в чате, зайдите в Supabase → Settings → Database → **Reset database password** и задайте новый. Publishable/anon key в `config.js` — публичный по дизайну, доступ к данным ограничивают RLS-политики.

## Возможности

### Новое в v1.07.18
**Журнал действий сотрудников (админ) — функция ядра.** Действия совершаются и с телефонов, поэтому журналирование встроено в мобильную базу (app.js), а ПК-режим наследует его автоматически — это разрешённое направление зависимости.
- Новая вкладка **«Журнал»** в меню (в ПК-режиме — слева), видна только админу. Фильтры по действию и сотруднику, кнопка обновления, постраничная загрузка по 300 записей («Показать ещё»), у записей об инвойсах — кнопка «Открыть».
- **Что попадает в журнал**: регистрация (пишется серверным триггером — клиент в этот момент ещё не авторизован), создание сотрудника админом, блокировка/разблокировка, смена роли, смена своего пароля, сброс пароля сотрудника, создание/изменение/удаление инвойса, «работа выполнена» и возврат в черновик, апрув (фиолетовый чип), изменения бригады (назначение/снятие коворкеров), выполнение пикапа, досрочный вывоз, продление аренды.
- **База данных**: отдельная таблица `audit_log`. ⚠️ Для существующей базы выполните **`supabase/update-to-1_07_18.sql`** (идемпотентен). RLS: писать можно только от своего имени, читать — только админ; политик update/delete нет — журнал не правится через API вообще; история хранится полностью, без автоматической обрезки (удалить записи может только владелец проекта вручную в SQL-редакторе). Без апдейта журнал работает локально на устройстве, а приложение подскажет обновить БД.
- **Локальный диагностический лог** увеличен до **2000 строк** (хранение и просмотр в «Настройки → лог»).

**ПК-режим (десктопный слой):**
- **Верхняя панель формы инвойса**: липнет под шапкой; иконки без подписей — «История работы», галочка «Работа выполнена» (двусторонняя синхронизация с нижней), **фиолетовый индикатор апрува** (только состояние, без стоимости), живой «Итого», «Скачать PDF». Ничего не надо прокручивать вниз.
- **Апрув — фиолетовый везде**: индикатор в панели, чип в журнале, рамка карточки «Поставить апрув» и пометка апрува вместо жёлто-зелёных.
- **Чипы периодов** «Все даты · Сегодня · 7 дней · 30 дней» над результатами при выбранном в колонке сотруднике: работы фильтруются по дате работы, пикапы — по сроку вывоза (даты берутся из локального кэша, спорные карточки не прячутся).
- **Память последнего сотрудника**: выбор в колонке сохраняется между сессиями и применяется при входе; «Все» сбрасывает.
- **Горячие клавиши**: 1–9 — вкладки меню по порядку, Esc — закрыть модалку.
- **Плотность интерфейса**: кнопка ≡ внизу слева переключает «просторно/компактно» (запоминается).
- Отложено из идей: сплит «форма | живой предпросмотр PDF» — требует вынести генератор PDF из ядра наружу (output в data-URI вместо скачивания); сделаю отдельным шагом по команде, это одна аккуратная правка app.js.

Любую ожидающую строку — пикап или продление — можно **аннулировать досрочно** кнопкой «Забрать сейчас», оборудование помечается вывезенным раньше срока.
- Пересохранение работы больше не трогает строки, затронутые продлениями: форма Equipment Rental управляет только «нетронутыми» исходными пикапами.

### Новое в v1.07.10
- **Общий доступ к документу для коворкера**: в форме работы, в блоке «Кто выполнял», появилась галочка **«Общий доступ к документу для коворкера»** — её видят и переключают только автор работы и админ. Когда она включена, сотрудники, добавленные в бригаду, видят эту работу у себя на главной наравне со своими (с именем автора и синим чипом **«Общий»**), могут открыть и редактировать её: содержимое инвойса, заметку, отметку «Работа выполнена», скачивание PDF; работа видна коворкеру и во вкладке «Отчёты». Пикапы оборудования по такой работе тоже отображаются у коворкера — он может их забирать, они попадают в его баннер-напоминание. Состав бригады, сама галочка доступа и удаление документа остаются за автором (и админом): коворкер в чужом документе видит бригаду без кнопок редактирования и синюю пометку «Автор включил общий доступ».
- **Выключатель для админа**: «Настройки» → карточка **«Общий доступ к документам»** → галочка «Разрешить общий доступ к документам для коворкеров». Если её снять, функция отключается для всей команды: галочка в работах скрывается и перестаёт действовать, каждый делает документы сам. Отметки в самих документах при этом сохраняются и снова заработают, когда админ включит функцию обратно.
- ⚠️ **Для существующей базы** выполните в SQL-редакторе Supabase файл `supabase/update-to-1_07_10.sql`: он добавляет колонки `jobs.shared_with_helpers` и `org_settings.allow_shared_jobs`, функции `shared_jobs_enabled` / `is_shared_job_helper` и обновляет RLS-политики работ и пикапов, чтобы коворкер мог видеть и править общие работы со своего устройства. Скрипт идемпотентен: повторный запуск безопасен. Без него общий доступ действует только локально у автора, а приложение при сохранении подскажет обновить БД (данные при этом не теряются — запись повторяется без нового поля). Если вы обновляетесь с версии старше 1.07.07 — сначала выполните `supabase/update-to-1_07_07.sql`. Новая база с нуля разворачивается полным `supabase/schema.sql` — отдельные update-файлы тогда не нужны.

## Код приглашения
Хэш кода лежит в таблице `app_secrets` (RLS без политик — прочитать её могут только серверные функции). Сменить код:
```sql
update public.app_secrets
set value = encode(sha256(convert_to('ВАШ_НОВЫЙ_КОД','UTF8')),'hex')
where key = 'invite';
```
Рекомендуется сразу заменить `APC` на длинную фразу (12+ символов): хэш из публичного репозитория короткий код можно подобрать перебором.

## Подключение Supabase
1. Создайте проект на supabase.com (регион любой).
2. **SQL Editor → New query** → вставьте содержимое `supabase/schema.sql` → **Run**. Создадутся таблицы, RLS-политики, триггеры и сид-справочники (виды работ, оборудование, PRICE).
3. **Authentication → Sign In / Providers → Email**: выключите **Confirm email** — это обязательно, потому что вход идёт по логину, а служебные адреса вида `login@techlog.example.com` письма не получают. Пользователи регистрируются сами в приложении (логин + пароль + код приглашения) либо создаются в дашборде: Authentication → Users → Add user, email вида `login@techlog.example.com` (тот же домен, что в `config.js`).
4. Назначьте роли (SQL Editor):
   ```sql
   update public.profiles set role='admin'   where login='admin@example.com';
   update public.profiles set role='manager' where login='manager@example.com';
   -- остальные по умолчанию 'tech'
   ```
5. `config.js` уже содержит Project URL и publishable key этого проекта — если создадите другой проект, замените значения там.
6. Первый вход: зарегистрируйтесь в приложении (или создайте пользователя в дашборде), затем назначьте себе `admin` SQL-командой из шага 4. Дальше роли меняются прямо в приложении: Справочники → Сотрудники.

## Приватный репозиторий и хостинг
На бесплатном тарифе GitHub Pages публикует сайты **только из публичных репозиториев**; приватный репозиторий + Pages требует план GitHub Pro. Варианты:
1. Оставить репозиторий публичным — это безопасно: в коде нет секретов (publishable key публичный по дизайну, код приглашения хранится хэшем, пароль БД нигде не используется).
2. Сделать репозиторий приватным и деплоить бесплатно через **Cloudflare Pages** или **Netlify**: они подключаются к приватному GitHub-репозиторию, настройка — «Framework: none, Build command: пусто, Output: /», деплой на каждый push.
Само приложение в любом случае открыто по ссылке, но без логина не показывает ничего, а регистрация закрыта кодом приглашения.

## Защита базы данных — чек-лист
- **RLS включён на всех таблицах** (уже в схеме): анонимный ключ без активной сессии не читает ничего; каждая роль видит только разрешённое.
- **Смените пароль Postgres** (Settings → Database → Reset database password) — он пересылался в переписке. Никогда не кладите его и `service_role key` в репозиторий или клиентский код.
- Регистрация закрыта **кодом приглашения** с серверной проверкой; смените дефолтный `APC` на длинный.
- В Authentication → Settings включите **минимальную длину пароля 8+** и защиту от утёкших паролей (Leaked password protection).
- В Authentication → Rate Limits оставьте лимиты по умолчанию — они тормозят перебор логинов/кодов.
- Supabase делает **ежедневные бэкапы** (Database → Backups) — проверьте, что они включены; перед крупными изменениями можно скачать дамп.
- Периодически просматривайте **Auth → Users** на предмет незнакомых аккаунтов; лишнего удалить, код приглашения — сменить.
- Продвинутое (по мере роста): Network Restrictions для прямых подключений к Postgres (платные планы), отдельный ключ на окружение, аудит через Logs.

Она проверяет всё по цепочке и показывает отчёт (его же печатает в консоль и даёт скопировать): версия клиента и сервера, загрузка CDN-библиотек, доступность Auth API и REST API, наличие сессии, существование таблиц (`profiles`, `work_types`) и **функции `check_invite`** — если schema.sql не выполнялся или откатился, отчёт прямо напишет «выполните supabase/schema.sql целиком». Кроме того, приложение постоянно пишет журнал в консоль браузера: каждая строка вида `[TechLog 1.03.03 2026-09-03 14:22:31] …` — старт, вход, регистрация (включая ответ проверки кода приглашения), синхронизация и все ошибки; последние 20 событий попадают в отчёт диагностики.

Важно: сообщение «Неверный код приглашения» теперь означает именно неверный код. Если на сервере нет функции проверки — будет отдельное сообщение «Сервер не настроен: выполните supabase/schema.sql».

### Регистрация: точные причины отказа (v1.03.04)
- Форма регистрации проверяет логин на занятость «на лету»: как только вы уходите из поля логина или ставите курсор в пароль, под полем появляется «✓ логин свободен» или «⛔ Такой логин уже существует» (RPC `login_available`).
- Перед отправкой клиент вызывает `signup_precheck(login, invite)` и показывает точную причину: занят логин / неверный код / плохой формат. Триггер `handle_new_user` бросает те же коды (`LOGIN_TAKEN`, `BAD_INVITE`, `BAD_LOGIN`, `PROFILE_CREATE_FAILED: …`), так что в Supabase → **Logs → Postgres** причина любого 500 видна открытым текстом.
- Проверить «хвосты» от неудачных попыток можно в SQL Editor:
  ```sql
  select id, email, created_at from auth.users order by created_at desc;
  select id, login, display_name, role from public.profiles;
  ```
  Лишнего пользователя удалит `delete from auth.users where email = 'логин@techlog.example.com';` — профиль удалится каскадом, логин освободится.

## Если приложение «зависло» на заставке
С v1.03.02 такого молчаливого зависания больше нет: через 6 секунд встроенный сторож сам покажет диагностику — что не загрузилось (app.js, config.js, supabase-js), какая версия лежит на сервере и какая ошибка случилась, плюс кнопку **«Сбросить кеш и перезагрузить»** (сносит service worker и все кеши). Типовые причины и лечение:
1. **Залиты не все файлы** — откройте `https://<логин>.github.io/<репо>/version.json`: версия должна совпадать с ожидаемой. Если нет — перезалейте весь комплект, особенно `app.js`.
2. **GitHub Pages ещё собирается** — после пуша подождите 1–2 минуты и обновите страницу.
3. **Старый кеш браузера/SW** — Ctrl+F5 (на телефоне: закрыть вкладку и открыть заново) или кнопка «Сбросить кеш» на панели сторожа. С v1.03.02 JS и CSS ходят по схеме network-first, так что смешение старой и новой версии после деплоя исключено.
4. **Не грузится CDN** (supabase-js/jsPDF/Leaflet) — сторож это покажет; проверьте интернет/фаервол.

## Как выпустить обновление
1. Измените версию в **трёх** местах: `app.js` (`APP_VERSION`), `sw.js` (`VERSION`), `version.json`.
2. Закоммитьте в `main`. При следующем открытии страницы приложение подтянет новый service worker, перезагрузится и покажет «✓ Приложение обновлено до версии …». Если у пользователя открыта форма работы — обновление применится после её закрытия (данные не потеряются).

## Карта и геокодинг
Карта работает на Leaflet + OpenStreetMap и не требует API-ключей и биллинга. Кнопка «Найти по адресу» обращается к бесплатному геокодеру Nominatim (лимит ~1 запрос/сек — для ручного заполнения справочника этого достаточно). Ссылки «Открыть в Google Maps» и «Маршрут дня» открывают штатное приложение Google Maps с точками/маршрутом — навигация происходит там.

## Голосовой ввод
Используется Web Speech API браузера: Chrome на Android и десктопе распознаёт RU и EN «из коробки» (нужен интернет). В iOS Safari и Firefox API недоступен — там заметку набирают с клавиатуры, приложение честно сообщит об этом.

## Примечания
- Демо-режим и Supabase-режим используют одинаковые структуры данных; localStorage служит офлайн-кешем и в Supabase-режиме.
- «Другие услуги» на инвойсе — три свободные строки с суммами (попадают в PDF как рукописные строки формы).
- Push-уведомления вне открытого приложения в v1 не включены; баннер и пикап-лист появляются при каждом открытии/синхронизации.
